## Actual local overlap and the source of the new action

Current `dist/bundle-exchange-core.mjs`/`-ui.mjs` conserve one collection while ten ones wrap and unwrap. `dist/joining-orders-core.mjs`/`-ui.mjs` already own two frozen version-1 source pairs, `24+13=37` and `24+17=41`, with per-origin counter moves, an optional typed total and saved check/Keep snapshots. The Join model may be separate, partially framed or wrapped; the existing written material is an equation prompt and a proposed number, **not two aligned place-value columns whose result digits are placed from the grouping**. Reusing those exact pair identities and their frozen source avoids a new catalog and historical-source ambiguity. Spec 107's ledger picture is a separate transient teaching view of the same source; it does not reinterpret a saved Join grouping as a child's written procedure. The two sources represent seven loose ones without an exchange versus eleven loose ones with one new ten and one leftover. These two finite cases suffice for the first contrast; an exact-ten/zero-ones result and larger algorithms remain separate work.

The current `dist/bundle-broad-exposure.mjs` reads finite `shownBundleExamples` lists from Bundle, Join, Returning and Comparison. A generated broad `bundle` variant can use any one-to-nine tens and zero-to-nine ones (`dist/broad-variants.mjs:draw/validBroadParams`). Showing the Join operands or completed canonical ledger can therefore disclose an answer that a later broad task might otherwise mark fresh. Joining's existing list already admits the exact five possible ledger signatures: `2:4`, `1:3`, `1:7`, `3:7`, `4:1`, encoded as `bundle:0:tens:ones`. The narrow design records only a complete *actually visible* number-and-grouping pair in that existing field, with `noteJoiningExamples` and current broad familiarity syncing. It changes neither the Join source/schema nor an independent answer. An entirely unsaved route was rejected for this concrete exposure failure; a new top-level root was rejected because a started Join case already owns the source and finite exact-display field. If an old Join root is unreadable, the new view must use its current recovery boundary instead of inventing a playable source.

## Primary mathematics guidance and exact design limits

The official [Common Core `2.NBT.B.7`](https://www.thecorestandards.org/Math/Content/2/NBT/B/7/) asks learners to connect concrete models/drawings and place-value strategies to a written method, including sometimes composing tens or hundreds. Its scope is within 1000 and includes addition *and* subtraction; the two sums here are a much narrower guided example. The UK [NCETM Algorithms: column addition, topic 1.20](https://www.ncetm.org.uk/classroom-resources/primm-120-algorithms-column-addition/) explicitly names aligned addend digits, ones-first column work, and regrouping when a column reaches ten or more. The [NCETM Dienes/place-value counter guide](https://www.ncetm.org.uk/media/8d84e7959f5fd34/ncetm_ks3_representations_dienes_pv_counters.pdf) discusses keeping blocks beside written symbols so that trading ten ones for a ten remains visible. These sources support the *representational relationship*, not this app's efficacy, a mandated method for every learner, or permission to call a supplied digit placement independent performance. The first case has `4+3=7` and `2+1=3`; the second has `4+7=11`, exchanges ten of those ones, leaves one, then counts `2+1+1=4` tens. Every on-screen mark/annotation must honor those identities and the origin of each counter.
