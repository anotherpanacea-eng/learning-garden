# Fair Test Bench — choose what a comparison can tell us

Status: **build-ready** after [independent six-lens specification review](../reviews/56-fair-test-spec-review.md); implementation and release gates remain separate.

## Purpose and boundary

The town has repaired its first ramp. Now the parcel crew wants evidence for a longer landing lane and a short porch delivery. Extend the Workshop's original six-setting ramp model into a **learner-designed comparison**: choose a question, build two setups, notice what changes, predict, repeat, and advise the crew. The existing Workshop automatically holds one factor fixed. This desk deliberately allows the same setup twice, the wrong factor, or both factors changing, then explains what those comparisons can and cannot tell us. No failed test blocks play.

This is practice designing comparisons in an authored model, not proof of physical experimental competence. No new biological/physics dataset, simulated randomness, average, probability, force calculation, broad mastery, adaptive placement, points, timer, inventory or film is added. A later fair plant-growth test can reuse the pattern after its own content/model review. The [source audit](../source-audits/56-fair-test-bench.md) defines the exact narrow source links.

## Three short pages

Keep a compact mission card, A/B setup summary and authored-model notice beside each current prompt. All three pages are open at all times: **Plan → Try → Tell**. Navigation, reload and leaving preserve work. A return link leads to the Workshop. One primary action and one short question should be clear at each turn; older investigations stay in a disclosure.

1. **Plan.** Choose one of two missions: `height` ("Does changing ramp height change the landing distance?") or `surface` ("Does changing the landing surface change the distance?"). The crew's longer-lane/shorter-porch purposes provide context, not an assumed answer. Each setup has height `low|middle|high` and surface `smooth|rough`; A and B are independently editable. The same cart, no added push, distance measured horizontally from the ramp foot and the authored units are always held constant. Show two small apparatus pictures with text equivalents. A live **comparison check** distinguishes `same` (neither factor changes), `confounded` (both), `wrong-factor` (only the other factor), and `focused` (only the question's factor). These are explanations of setups, not grades. For a confounded pair: "Both changed. A different stop cannot tell us which change caused it." For an identical pair: "Repeats can show variation, but this pair does not compare different [target] settings." Allow all pairs to run.
2. **Try.** Optional prediction `A|B|similar|unsure|null`: "Which setup might go farther?" Keep prediction and whether any result had already appeared separately. Each button reveals **one new trial** for A or B, independently; there are three authored trial values per setup. Reuse the exact distances already present in the original six configurations. A trial is immediately frozen with setup id, trial index (1–3), distance (integer0–30), unit code `model-cm` and source code `authored-ramp`. No time, physics animation, automatic trial or random generation is needed. A static landed cart and marker move only on a requested reveal. Show a common zero-based0–30 ruler, all revealed marks and a small A/B table, with missing cells labelled "not tried". Counts and units stay visible. "Three examples in this model" is explicit; no fourth result cycles and pretends to be new evidence. Replay merely selects an existing row. Trials are observations; a claim is separate. Before both sides have results, say evidence for a comparison is missing. With unequal counts, invite matching repeats rather than declaring a winner. With three per side, show each observed minimum–maximum and describe whether those actual frozen repeats differed. Do not imply three is universally sufficient for a real investigation.
3. **Tell.** Choose a provisional claim `A|B|similar|not-enough|null` and an optional exact original note (up to800 characters). The app does not grade that prose or prediction. A supplied evidence summary names the actual frozen measurements and comparison design. When the pair is confounded/wrong-factor/identical, retain its results while explaining its limited relevance to the chosen question. A valid focused pair with equal nonzero counts may say "In these shown model trials, every A distance was larger than every B distance" (or reversed), only when that statement follows from the shown intervals; otherwise show overlapping ranges, without inferring equality. The child can keep an unfinished investigation, use speech with a grown-up without entering text, return to collect more, or start a new one. No compulsory answer or success state.

Changing a setup or mission **after any reveal** must not silently relabel or discard those trials: keep the current investigation as it was and begin a new investigation with the edited plan. Explain this before the first edit and in the resulting status. Prediction-only edits do not start a new investigation. Before any reveal, setup edits update the current plan. New investigations copy no prediction, prose, help or outcome into an independent attempt. They remain familiar because the same finite model has been visited; no mastery inference follows. Keep up to12 investigations, including the current one; disclose this limit next to the history and before starting another at capacity. Explicitly starting another may evict the oldest readable investigation; unsupported raw entries remain in place. At capacity, an edit that would fork an observed investigation does nothing and explains that the learner must explicitly use “Start another” (with the oldest-readable eviction disclosed) before editing; this prevents silently evicting the very observation being preserved. Ordinary rendering/navigation cannot evict work.

## State and saved-work rule

Use one optional `fairTests` root with `version:1`, `page:plan|try|tell`, `current` positive integer id, `nextId` positive integer, `seen` boolean and `investigations` (at most12 readable entries; unsupported raw items are retained in place). Each investigation has `id`, `mission:height|surface`, `a` and `b` known configuration ids, `prediction`, `predictionAfterResults` boolean, `claim`, `note` string≤800, `support` (distinct enum codes `help|audio|together`), `familiar` boolean, `trials` (at most6), `selected:{side:A|B,index:1|2|3}|null` referring to an existing row, and `kept` boolean. Trials have the stable fields above plus `side:A|B`. Require unique `(side,index)` pairs and each row's setup id to match that side's investigation setup; contradictory rows make that investigation unreadable, not its siblings. Selection references an existing `(side,index)` pair. The model's current next reveal is the first missing index for that side. No invariant ties reported support/familiarity/claim to a generated verdict; no display-text equality or saved-result recomputation on load. Stable numeric bounds, ids and enums protect rendering; historical distances are read as saved even if current model numbers change. Render historical units/source through codes.

Root reading is pure. Missing root renders an invitation; only the first explicit action creates it and records familiarity. First view is not used as independent assessment; all work is labelled practice. A present version1 root with one malformed investigation keeps valid siblings playable and retains the raw malformed item in a read-only "Earlier work" disclosure; do not overwrite or force a whole-game reset. A future/invalid envelope remains exact and read-only; show a clear explanation and leave the old Workshop usable. Do not require a new recovery-state framework. Preserve unknown fields, other roots and original note whitespace/newlines through load, ordinary actions and transfer. Escape every note and raw payload in HTML. Set textarea `.value` after render if necessary to preserve a leading newline. No network, microphone, uploaded data, new learner profile fields or external service.

Editing one invalid current item can choose another valid sibling or explicitly start another, retaining unreadable originals. Existing valid frozen trials survive updated message wording. Do not re-run old tests to validate a save. Kept status is a learner bookmark, not task completion; later edits unset it and retain the work.
