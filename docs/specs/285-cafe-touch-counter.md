# Spec 285 · Café touch counter

**Author-frozen candidate for independent spec review, 2026-10-28.** Carry the released Two Letters touch pilot's compact, native-control play surface into the existing replayable café. Make the plate and jars the play, with less text between the child and the next useful action. This is a presentation increment, not a new learning capability. New/repositioned short labels are in [the copy sheet](../content/285-cafe-touch-counter-text.md).

## Frozen scope

Keep the same guests, wishes, orders, recipe counts, stock, discoveries, repairs, number questions, support, feedback, gathering, serving and six-table supper. Keep every existing route, explorer, notebook root, notes download, transfer, save-off and reset behavior. No new café core state, source schema, action rule, answer key, lesson, Marble mapping, adaptation, historical grading, achievement, network service, drag requirement or framework. No new source/content pack is needed. If implementation cannot satisfy this contract without changing an action rule or durable state, name the concrete blocker and return for a bounded spec amendment before making that change.

The surface applies to exact `#cafe`, including resting, plate/repair, total, stock and served views. Other café benches and the explorer picker keep their existing frames. Preserve the old generic café fallback's behavior for other URLs; do not silently apply new chrome to all `root==='cafe'` dispatches.

Mandatory decisions: native jar buttons add one bite; filled plate buttons remove one bite of their ingredient; one plate editor; explicit checking; available jars paged six at tablet/desktop and four on phone; local view state only; ordinary document flow. No open design question blocks this candidate. Independent review may identify a bounded correction before root freezes it for build.

## Counter design plan

Subject: an imaginary garden café, operated with a finger or keyboard, welcoming one waiting guest. Spend the visual emphasis on the plate and its recognizable foods. Keep the forest ink `#183f39`, mint counter back `#eaf4ef`, paper plate/ticket `#fffef9`, yellow jar/primary accent `#e9b84a`, rose character accent `#da8d8d`, and wood counter edge `#b99b74`. These are existing café materials/colors, not a new theme. Georgia names/headings, Trebuchet controls/body; retain the app's fallbacks, no font downloads. Reading and controls use at least16px; decorative art may shrink, instructions may not.

Tablet layout, left-aligned labels with a centered plate:

```text
exit       Almost-Right Café       explorer / Notes
portrait + name   [wish] [wish]   guests · bites each / Hear
           one plate, its bite count, current feedback
                 Check my plate
 [jar] [jar] [jar]        each jar is one native add button
 [jar] [jar] [jar]        names, wishes, stock, chosen count
 Previous jars       shelf n of m       More jars
Go gathering          Café tools (closed)
```

At <=620px show four jars in two columns, portrait/order compactly above the plate, without narrowing labels below readable size. At >=621px show six in three columns. Six-card last pages may contain fewer actual jars; do not create dummy choices. At320px the page scrolls naturally. At820 portrait and1024×768 landscape, the ordinary small-order view must show the guest/order, plate, Check and first Add control within the initial viewport, without scrolling past prefatory lessons. Long12×12 orders and200% zoom may scroll; do not force a fixed-height viewport or clip content to achieve compactness. Twelve slots wrap into countable rows, never a single compressed line. No sticky/fixed bar, overlay cupboard or overlay tools. Expanded tools push following content down.

Design critique before build: the current separate guest column, long order ticket, plate panel, chosen-ingredient list, second shelf check bar and full jar catalogue repeatedly describe one plate. Replace that repetition with one counter and one editor. The distinctive elements are the original guest, actual requested qualities and edible-shaped bites; avoid generic equal-card dashboards, decorative headings or new gradients. Keep jar shapes quieter and shorter so their controls and actual food carry the meaning. Screenshot critique must check this actual density, not only matching selectors.

## Plate, jars and explicit feedback

The compact order strip always shows the current guest portrait/name, the two quality icons **with text**, number of guests, bites per plate and Hear the order. Keep full greeting/sold-out dish/story explanation reachable in tools, not as a first-visit obstacle. The short fictional-food notice remains available without relying on colors or pictures alone. Do not auto-open the long introduction for a first visit. Starting/resuming an order follows the current explicit app route/action path; rendering never creates an order.

Render one plate from `currentRecipe`, with the requested normal slots. Accepted saved recipes may contain up to12 selected bites even when the current request needs fewer. Never hide those selected units when removing the parallel editor: after the normal spaces, show every remaining selected bite in a clearly labelled Outside the requested spaces area of the same editor, with the same native ingredient removal controls. Keep the actual chosen/needed count and recipe unchanged; do not silently trim, rebalance or check it. Empty slots are inert visual spaces, not fake add buttons. While stage is plate (including an open repair), each filled slot is a native `button type=button` with food art and ingredient name. Its accessible name is “Take one {ingredient} off the plate”. It calls existing `adjustBite(state,id,-1)`. Repeated ingredients are repeated count units; removal decrements that ingredient once, then redraws the sorted counts. It does not promise positional placement or persist a slot index. Do not keep the old parallel Remove one list/editor as a second editing interface. Do not wrap interactive buttons inside a `role=img` container that hides them; use a labelled group with a textual plate count/description. In total/stock/served, the plate is a non-editable representation; total retains explicit Change my plate.

Each available jar is a native add button card containing its original food art, name, labeled qualities, actual stock and chosen count. Card activation calls only `adjustBite(state,id,1)`. Its computed accessible name/description must include the ingredient name, qualities, actual stock and chosen count; a short action aria-label must not hide these descendant details. Use aria-describedby with actual visible detail IDs as appropriate, including for zero-stock and full/disabled cards. No nested button/link inside that button: gathering remains a separate link/control. A full plate disables add cards, keeps the page controls enabled, and explains removing a bite to make room. A zero-stock available jar remains selectable for planning; no click grants stock. Undiscovered foods do not appear as selectable jars, including through paging. All eleven are reachable after actual discoveries; the eight starters continue to satisfy all requests.

Keep one primary Check my plate beside the plate/shelf, with count and feedback nearby. Only activating it calls `checkPlate`. Adding/removing/paging/opening tools never records a plate check, auto-advances a valid plate, supplies a correct ingredient, alters wishes, or claims correctness. Keep the existing changed-plate feedback until the child checks explicitly. Preserve the two-wish rule: separate bites may supply the wishes, one bite may supply both, and repeated bites are allowed; its explanation remains available in tools and the live wishes/count stay visible.

An unsuccessful explicit check keeps the same live plate and jars editable, and presents the current `repairQuestion` alongside/below this editor rather than replacing it with a different large plate screen. Preserve the exact repair prompt, choices, feedback, help and Change my plate escape. Slot/jar edits use `adjustBite`, which closes the repair without creating another question. Answering a repair only records its response; a correct response uses existing `leaveRepair` to return focus to the editor, without fixing the recipe automatically. Incorrect responses retain the same question. New repair questions arise only from another explicit failed Check. Keep repair history/support exactly as the core supplies it.

## Local view, saved work and events

Use a small module-local café view record, not a notebook field: current notebook object identity + current orderIndex (or resting sentinel), shelf page, breakpoint page-size and tools-open state. Retain it across `renderCafe`/save/rerender for the same owner/order, including add/remove, a failed check, repair exit and total→plate return. Returning from gathering with the same notebook/order may reuse that page; it must not lose game state. New order, explorer change/import/reset clears it to page1/tools closed; switching away and back must not inherit another explorer's page. Explicit reset helper in existing app lifecycle seams is sufficient. Reload starts local view at page1; durable work resumes its saved stage. No global `localStorage`, URL parameter, shared page across explorers or persistent view schema.

Page availableIngredients in stable authored order. Clamp page to `0..ceil(available.length/pageSize)-1` on discovery changes or breakpoint resize, ensuring the current visible range stays valid. Buttons at boundaries disable; show shelf number/total. Page changes redraw only UI; they do not call café actions/save a mathematical observation. At a resize, page1 is an acceptable deterministic fallback; never hide the last jars or strand focus in removed controls. Keep focus on the activated jar after adding if enabled, otherwise on plate count/editor heading; slot removal returns to the same ingredient if still present, otherwise to the plate heading. Page actions focus the shelf heading/readout. Failed check→repair heading; successful check→total heading; revise/repair leave→plate heading; serving→response or newly complete supper heading. Use visible focus and `scrollIntoView` as necessary.

Every native handler must guard its connected captured café root, currently active notebook/explorer, current order identity/index and captured stage before mutation, save, focus or exposure. A disconnected old jar/check/number form/serve/next/range/supper control must be inert after rerender, route exit, explorer switch, reset/import or stage transition. Do not invent historical order validation. Disable/reject repeated native dispatch from the old DOM after a successful action; core idempotence remains the serving backstop. Guard input and submit as well as button clicks; retain `numericAnswer` and0..999 parsing/error semantics.

No persistence migration, new evidence field or new record cap. Keep version1 café, stock0..180, recipe/per-plate total<=12, number attempts and plate attempts latest50, repair-history and served/skipped history latest24, existing order/counter ceilings, and all original normalization/recovery behavior. Do not newly regrade earlier observations against today's content. Keep valid legacy params/missing-params recovery and closed-order protections; no new validator is introduced by this spec.
