# 84 · Willow Sorting Desk: one rule, two branches

**Status:** Author draft for independent specification and content review. No runtime, atlas change, merge, or deployment is authorized by this document.

## The small gap

Willow Post Office already lets a courier follow an ordered, literal flight plan. [Instructions for a Reader](54-instructions-for-a-reader.md) lets a child test the order of supplied actions and discuss a reader's knowledge. Neither lets the child set a condition, see which of two branches a deterministic machine takes, and revise a rule after a contrasting input. Add one optional **Willow Sorting Desk** entry on the `#post` hub. It is a tabletop machine in Pip's fictional post office, separate from delivery visits, packing, letters, and the instruction notebook. Every existing destination stays open. A sorting check neither delivers a parcel nor creates a Post Office `visit`.

The child makes one visible rule: **If [condition], put it in [basket]; otherwise put it in [basket].** A parcel supplies a stamp shape and a wrapping color. The child may predict a basket, then step the machine through **read input → test the condition → take exactly one branch**. The result is compared with Pip's request, which describes an intention, not what the machine secretly does. The child can edit either branch or the condition, reset the trace, and test the same or another parcel. There is no generated code, AI, learning model, timer, score, penalty, success gate, adaptive suggestion, or loop construct. Repeated parcel tests are repeated executions of one authored rule, not a claim that the child understands every computing topic.

## Complete first pack and contrast

The authored source ID is `willow-stamps`, version 1. Its visible request is: **“Pip asks: Put parcels with a star stamp in the Lantern basket. Put every other stamp in the Leaf basket. Look at the stamp, not the wrapping color.”** The basket labels are **Lantern basket** and **Leaf basket**. Each parcel is a fictional card with a large stamped **star** or **circle**, a separately labeled **blue** or **yellow** wrap, and distinct outline/pattern cues. Color never carries the only clue. The source snapshot contains this exact request, labels, all four parcel titles and feature values, the short help/feedback lines below, and the intended request rule `{feature:'stamp',value:'star',then:'lantern',else:'leaf'}`. Drawing and accessible text are generated from the saved values; there is no uploaded photo or address.

| Parcel | Exact title and visible features | Request's basket | Contrast |
| --- | --- | --- | --- |
| `star-blue` | **Blue parcel, star stamp** | Lantern | Stamp and color happen to agree. |
| `circle-yellow` | **Yellow parcel, circle stamp** | Leaf | Stamp and color happen to agree. |
| `star-yellow` | **Yellow parcel, star stamp** | Lantern | A blue-wrap rule now disagrees with the request. |
| `circle-blue` | **Blue parcel, circle stamp** | Leaf | The other color pairing tests the else branch. |

All four cards are selectable from the start. The first pair is suggested as a starting comparison, and **Try a contrasting parcel** selects `star-yellow`; it never unlocks a card or silently runs a test. A child can also select `circle-blue` first. The current program begins unset; the three native selectors are **Condition** (`stamp is star`, `stamp is circle`, `wrap is blue`, `wrap is yellow`), **Then basket**, and **Otherwise basket** (each has both baskets). Both baskets may deliberately be the same: this is executable, but may not serve Pip's request. There are 16 finite programs. A condition reads one feature only; `otherwise` handles every input for which that condition is false. Nothing interprets a parcel's color as a stamp, or infers a rule from an answer or a typed sentence.

The copied teaching lines live in `source.text` under the keys `intro`, `help`, `predictionPrompt`, `otherBranch`, `fit`, `mismatch`, and `counterexample`. The displayed basket comparison is assembled from the saved basket labels and saved request rule, with no parsed prose or substitution in a learner-entered string:

- Intro: **“Pip has four made-up parcels. Build a rule, predict one basket, then watch the machine follow your rule. A machine follows the rule you set, even if Pip wanted something else.”**
- Optional help: **“A condition asks one yes-or-no question about this parcel. If it is true, the machine takes Then. If it is false, it takes Otherwise. Only one basket is used for a parcel. You can change your rule and try again.”** Opening this is marked as supplied support for later checks; it never chooses a rule.
- Prediction prompt: **“Before stepping, where do you think your rule will send this parcel?”** The choices are Lantern basket, Leaf basket, and **“I am not sure yet.”** A prediction is optional; `not sure` is not a wrong answer.
- After the condition step, show the observed feature and a text/symbol **Yes** or **No** result, highlight the selected branch, and say **“The other branch does not run for this parcel.”** No parcel moves yet.
- After the branch step, show **“Your rule sent this parcel to [basket]. Pip's request calls for [basket].”** Add **“This rule serves this parcel's request.”** or **“These baskets differ. You can change the rule and test again.”** This is a comparison between the supplied rule and supplied request; it is not feedback on the child's prediction or a grade.
- Counterexample invitation: **“Two parcels can fit a rule by coincidence. Try a parcel with the other color and the same stamp.”** This is optional, and does not claim the current rule is wrong before a run.

With `wrap is blue → Lantern, otherwise → Leaf`, the first two outputs fit Pip's request but `star-yellow` goes to Leaf. With `stamp is star → Lantern, otherwise → Leaf`, all four fit. These are examples to verify the machine, not a forced solution path. A program can be edited after any step. Editing clears only the live trace and current prediction; it never changes an earlier saved check. Selecting another parcel also resets the live trace and prediction. **Start this trace again** resets the live trace on the same parcel while leaving the program and immutable checks. A branch step appends one check after the result is visible; mere selection, prediction, help, or condition-step exposure does not append a check.

## Place and interaction

The Post Office hub gains one short entry **“Try the Willow Sorting Desk”** after its delivery catalog. The desk has its own route, `#post/sorting`; it does not change `postOffice.current`, `postOffice.visits`, parcel packing, flight-plan clauses, or the instruction notebook. A direct route shows the small numeric-free intro and **Start a desk**; it does not allocate a save root until that explicit action. The four feature cards and full request appear only once a source copy has been allocated. A visitor with unfinished delivery can open the desk and return to exactly that delivery. A **Back to Willow Post Office** control is always visible.

Render the program as three labeled native selects and a read-only full sentence. Render the selected parcel as original still vector art plus the exact accessible statement “Star stamp; yellow wrap,” etc. Present one step at a time with a visible trace: input feature, condition result, taken branch, basket and request comparison. The inactive branch remains visible but marked “not taken”; it never receives an outcome. The child can change a choice, rerun, choose any parcel, open help, or leave without completing a set. Use buttons rather than dragging. At 320 and 820 CSS pixels, each control has a 44px target, no horizontal page overflow, sufficient contrast and non-color cues. Focus moves to the visible trace result after each step, to the changed rule sentence after an edit, and to the new card title after card selection. A single live status describes an explicit step; no autoplay, automatic speech or animation is required. If a local Hear control is offered, it uses existing narration, speaks only the visible saved source/trace, and records a request rather than verified listening.

The shelf never asks for a real child's name, address, photo, voice or package. The user may talk or gesture together; no oral answer is recorded. The grown-up note explains that a correct route is the deterministic result of supplied fields and a supplied request. A check records the selected program, optional prediction, visible steps and help exposure. It cannot establish independent coding, real-world classification, oral explanation, mastery, or the full Marble topic's repetition component. A repeated card is familiar practice, not a fresh independent attempt. No test result feeds an adaptive level, atlas mapping or another game.

## Saved work and recovery

Use one optional `sortingDesk` root, absent until **Start a desk**. A readable root has `{version:1,source,program,selectedParcel,prediction,phase,checks,nextCheck,support,retainedRaw?}`. `source` is the complete copied authored pack above. `program` is either unset or `{condition,then,else}` with one of the four condition codes and two basket IDs. `selectedParcel` is a source parcel ID. `prediction` is null, one basket ID, or `unsure`; `phase` is `ready`, `condition`, or `result`. The live trace is derived from the saved source and program at render, never from today's catalog; `phase:'condition'` requires a set program. A result phase requires a matching readable latest check; if that check is unreadable, show a safe unavailable-result notice and allow an explicit trace reset without rewriting the old check. `nextCheck` is a positive safe integer used only for local check IDs. `support` holds only sticky `helpOpened`, `together`, and optional `narrationRequested` booleans. All strings shown from `source` are escaped. No names, custom text, achievement flag or external data are stored.

Each immutable check stores a bounded monotonic local ID, its own parcel ID, program snapshot, optional pre-run prediction, condition input/value and true/false result, branch taken, actual basket, request basket, whether they match, and a pre-result support snapshot. Compute and validate these outcomes against the **saved source and saved rule**, not the current authored pack; a changed current request or card cannot regrade old checks. All checks use supplied cards and an editable supplied rule, so none is labeled a fresh independent demonstration; there is no familiarity or attainment flag to misread. The source is bounded to 12 KiB UTF-8; accepted v1 sources may hold 1–8 uniquely identified parcels with independently bounded titles and known stamp/wrap feature enums, two uniquely identified basket labels, a request rule using those own feature/basket IDs, and all seven required `source.text` lines. IDs use `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`; each title, basket label, request and teaching line is nonblank and at most 500 UTF-8 bytes. Do not require today's four IDs, count, order, labels, condition value or request wording. The four new authored cards still must pass a separate exact-pack check. Validate the live rule and phase against that same saved source. Unknown harmless keys remain preserved and ignored.

At most 12 checks fit in a root. A malformed individual check remains byte-for-byte as parsed raw data in its slot and is shown only as **“An earlier check is unreadable; it remains in your notes.”** Other checks and the live rule remain usable; neither loading nor rendering repairs or discards a sibling. Before a thirteenth check, refuse the new check atomically with **“This desk has room for twelve checks. Download your notes, then start a separate desk to keep testing.”** A check is never silently evicted. No check is required to proceed to another parcel. An invalid or future root/source/current program is read-only recovery: show a focused notice, **Grown-up notes**, **Back to Willow Post Office**, and **Start a separate desk** behind confirmation. Keep the entire original JSON value in the new root's `retainedRaw`, including prior recovery, without changing it; replacing a readable root carries its existing `retainedRaw`. Starting a separate desk from a readable root also requires confirmation and warns that the current checks will leave the active desk, so Download is available first. An unreadable check alone does not force whole-root recovery. Notes describe readable checks and support as reported context, and mention retained unreadable data without rendering arbitrary raw HTML; full raw data remains in the JSON download.

New Start, a check append and a confirmed recovery start preflight the **whole proposed notebook** through `prepareProgressImport` and the actual formatted `notesReport` callback used by Download. This addresses the real 5 MiB transfer cap, depth and node limits, including nested `retainedRaw`. If it fails, make no mutation, show an actionable notice to download current notes/start a separate explorer, and leave all other activities usable. Do not evict old records to pass the preflight. Quota refusal follows the existing in-memory work plus visible save warning and download access. Save-off, explorer switch, reload, local export/import and reset follow the existing shared notebook; a malformed `sortingDesk` root is permitted through the optional-root importer and preserved for local recovery without weakening other root checks. No new storage backend or generic schema registry is needed.
