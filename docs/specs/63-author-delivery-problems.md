## The new action

The market crew needs delivery requests as well as maps. “You know this map. Where should a courier start, what must they collect, and where should they finish?” A child chooses the **conditions of a problem**, then creates a separate solving sheet. The solution is still authored with the existing direction buttons; creating the problem does not copy a solution, claim a shortest route or require another human. This follows [PR47’s learner-posed-problem idea](https://github.com/anotherpanacea-eng/learning-garden/blob/058fcd271a09fd0b42ec9e74b154e673148de2c2/docs/other-routes-through-the-acts.md) in the existing Cartographer game.

Existing free maps already support placing landmarks and two routes; supplied jobs already add start → collect → deliver conditions. Neither lets a learner turn their own map into that request. Reuse those representations and job semantics. No new world, route shell, universal problem grammar, learner model, reward, private identity, upload, AI or time limit. The12-command route-card limit is a representation constraint, not a speed test. All locations and sealed parcels are original fiction; no real map/GPS or personal location. This first slice has **no free text**: the generated wording makes the selected conditions explicit. Optional human-read original words would be a separate later extension, not parsed or graded here.

## Exact content, conditions and feasibility

On a native **free map** with all four landmarks placed at distinct intersections, offer “Make a delivery problem.” The four names/symbols remain Post Office/P, Café/C, Garden/G and Bridge/B. These are the existing integer0–5 coordinates, across first then up, adjacent orthogonal intervals each one fictional model metre. Requiring four placed landmarks is this format’s complete-map constraint, not a claim that a child must master four-point plotting before posing any problem.

The author chooses three known IDs with native labelled selectors:

- **Start at** — the courier’s starting landmark.
- **Collect at** — the required intermediate collection landmark.
- **Deliver to** — the final destination.

Use the source free map’s current from/to as initial defaults, and the first other landmark in the existing key as the initial collection choice. Defaults are offered conditions, not evidence the child independently invented each one. Duplicates may exist while drafting so swapping selections is easy. A preview says “Choose three different places for this request” until the three IDs differ. This slice does not accept a request that collects at its start or returns to its start; those can be meaningful later variants, not logically impossible journeys.

Canonical request, with the selected names substituted exactly: **“Start at [start]. Collect a sealed parcel at [collection], then deliver it to [destination].”** This generated sentence is the checked request. The author is choosing its conditions, not being assessed for composing prose. Generated title: **“A delivery problem from our map.”** Map-reader card: name all four frozen landmark coordinate pairs, then **“Read across first, then up. North is up and east is right. Each move travels one interval.”** The resolving job retains freely revealable Map reader / Dispatcher / Both clues, default both; role labels do not prove any partner spoke, read or participated.

Before creation, compute the exact least possible number of moves on this **unobstructed orthogonal grid**:

`abs(start.x-collection.x) + abs(start.y-collection.y) + abs(collection.x-destination.x) + abs(collection.y-destination.y)`.

Each leg must change those horizontal/vertical differences; moving along one axis then the other attains the sum within the rectangle. This is not Euclidean straight-line distance, a pixel measurement or a general obstacle-routing rule. Show the two legs as a brief optional explanation: across intervals + up/down intervals for each, with the sum. No answer commands or required author test route are stored. Showing the planning calculation is supplied support, not evidence of independent distance calculation.

Creation is available only when that minimum is≤12. Preview text for a feasible request: **“This request can fit our 12-move card. These conditions need at least [n] moves; a courier can find their own route.”** For an over-limit request: **“These conditions need at least [n] moves. Our route card holds 12 moves. Move a landmark or choose another collection point before making this request.”** Let the child edit conditions or return to landmark placement without losing either map/routes/checks or the draft choices. This is a visible creation constraint, not a hidden failure after a solver starts. The new creation action rechecks current positions/conditions rather than trusting a stale preview.

Independent specification/content review must inspect these complete examples:

1. Post(1,1), Bridge(4,1), Café(4,4), Garden(1,4); Post → Bridge → Café needs3+3=6. EEE NNN serves; NNN EEE arrives but misses Bridge. Both are6 intervals. Do not compare a solver with the author’s exemplar.
2. Post(0,0), Bridge(5,5), Café(3,5), Garden(4,0); Post → Bridge → Café needs10+2=12. EEEEE NNNNN WW is12 and serves. The boundary is allowed, not13 or an off-by-one point count.
3. Post(0,0), Bridge(5,5), Café(0,1), Garden(1,1); Post → Bridge → Café needs10+9=19 and cannot be created on this12-command card. The authored free map, selections and any existing route checks stay available. Moving/changing a condition can repair it.
4. The first square map with Post → Bridge → Café also accepts NNN EEE SSS NNN: Café is passed early, Bridge reached later, and Café is the final endpoint at12 moves. Delivery is at completion; an early destination pass does not disqualify the route.
5. A route ending at the collection point has really visited it but has not served the final delivery. Blocked/untravelled suffixes and empty routes remain the existing distinctions. Only an actual intermediate visit before final completion serves a job.

## Manageable author and solver turns

Keep **#workshop/maps** and Map/Route/Compare. On a readable free map, a clearly labelled authoring entry is available near its ordinary next actions. If a landmark is missing, explain “Place all four landmarks to make a delivery request” and provide normal placement access; do not manufacture a new map or visit just by viewing the entry.

“Make a delivery problem” explicitly opens a small authoring turn **inside the existing Map page**, with a compact static labelled map, three selectors, generated request, feasibility preview and **“Make this request on a new sheet.”** The full36-point placement grid is unnecessary during this turn. The active question and creation outcome stay together; avoid putting the form beneath a full map, routes and every earlier check. Keep the explanatory calculation in a freely open native fold, with plain-language names/units. The author may close with **“Change our landmarks”** and return to the same free map. Route/Compare pages remain open and preserve the author draft. Returning to Map restores its explicitly open/closed authoring turn.

The creation action produces one new native job sheet, with empty A/B routes, default both clues and the generated frozen source. It does not set a solved/checked flag. Show **“Our request is ready on a new sheet. Try a route, or invite another courier.”** Native direction buttons, repairs, route checks and saved job outcomes work as before. A parent/child can take turns or one person can play both roles. No outcome requires both routes to succeed or a partner to be present. Any unblocked route≤12 commands that fulfils the frozen request is valid, including detours and retracing.

Store a small origin reference with the frozen job: `source.authored:{version:1,mapId:<source free-round id>}`. When that map remains readable, provide **“Open referenced map [id]”** to resume it. Its draft stays editable; making a revision creates another solving sheet instead of rewriting this one. If normal retention has removed it, say the referenced map is no longer in the retained list, while this job keeps its own exact map/request. Do not infer authorship/identity from an imported numeric reference. Optional unreadable/future origin metadata is retained as escaped work and does not invalidate an otherwise understood version1 map/request; no solver judgement depends on origin metadata.

All controls need native labels,44px targets, keyboard access, local focus and no horizontal overflow on phone/tablet. Selecting a condition focuses that selector, not the top of the full game. Creation focuses the new job prompt, failure the nearby status. Freeze the authoring turn’s native open folds only within its own map identity. New author controls/narration must not apply queued events from an old detached map to a different current map. No compulsory speech, mouse-only action or private typed information. Existing map help/narration are practice support, not independent authoring/writing evidence; scope native events to the map they actually belong to rather than inheriting a history-open state.

## Small state extension and preservation

Reuse optional `cartographer` version1, existing map12/readable and check8 caps, existing `newMap(state,source)`, native route evaluator and generic transfer. Add only optional `round.authorDraft:{version:1,open:boolean,from:<known ID>,via:<known ID>,to:<known ID>}` to free-map rounds. Allow duplicate selected IDs in a draft; validate distinctness for creation. Current map positions always supply the preview. No copied solution, private prose, author score, timestamp, separate task registry or second history is needed.

Missing child state has pure defaults but is only stored by an explicit open/change action. A present unreadable/future child draft stays exact and visibly retained; it cannot be silently replaced by defaults. Its underlying understood free map remains playable, with ordinary routes and checks intact. A new blank map provides a fresh authoring opportunity. This optional child must not cause the whole base map to disappear as unreadable merely because the authoring draft cannot be edited. Rendering never allocates, repairs, trims or mutates.

The new explicit creation function must build and validate the full frozen job **before** invoking the existing single allocation. Reuse `newMap` rather than allocating a blank sheet then patching it or evicting twice. Failed incomplete/duplicate/over-limit/unsupported/unsafe-ID creation is nonmutating. The frozen source has its own map, from/via/to, exact generated title/request/map-reader wording and origin reference. The source free round retains its map, both live command lists, old checks and draft choices, except ordinary disclosed cap eviction. Root current/page/selection can change to the new solving sheet as the existing starter does.

Before the creation click, disclose the exact count of oldest readable maps removed, including oversized imports. If the currently authored source map is among those to be removed, explicitly name that fact before the action: “This also removes the map you are authoring from; the new job keeps its map and request, but not its older routes/checks.” Download/return/other destinations remain open. No silent promise that original work survives a cap eviction. Preview/selection/resuming never evicts raw siblings or readable maps. Retain the existing raw-sibling, failed-id and unknown-field preservation rules.

**Creation feasibility is not historical validation.** Keep `validMapJobSource`/recorded check admission based on the existing understood shapes and source agreement. Do not reject an old otherwise readable job because its positions would exceed the new creation limit, compare stored booleans with a recomputed route, add an origin-pointer reachability requirement or require the current catalog’s text. Old request wording/maps/contradictory results remain frozen and displayed as recorded. Editing a source free map or its request draft cannot stale/change a solver’s frozen job; the solver’s own route/condition inputs continue to define check relevance. Author draft editing does not stale unrelated free-map route checks. Ordinary supplied jobs and free-map movement must retain their existing behavior.
