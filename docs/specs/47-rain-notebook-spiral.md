# Rain Paths → Field Notebook: chart a completed machine result

## Problem and bounded outcome

Rain Paths currently keeps a completed two-tray table and invites a visit to the cress-only Field Notebook. That thematic link does not carry the observed machine counts or let the learner construct a chart from them. Add one explicit bridge: freeze a completed Rain Paths result, select data useful to its runoff question, build a two-bar draft, read that draft, compare it with its source, and revise or keep it.

This is a second use of the same familiar, invented model result. It is not a new experiment, an independent transfer assessment, a real water measurement, a hydrology forecast or a safety verdict. The learner supplies the bar values; the app must not draw a correct chart automatically on arrival. Existing cress work, water-machine progress, earlier predictions, per-case tray/question/plan views and outlet plans remain intact.

The increment is finite: the four existing Rain Paths case IDs, one current water-chart draft and one latest kept water-chart draft per case. No generated datasets, new experiments, arbitrary uploads, terrain modelling, chart-type chooser or general chart framework.

## Explicit invitation and exact source

Add **Make a chart of this completed result** beside an actually completed current-run table and inside the existing kept-result return section. Either source is eligible without an extra Keep step. Label the chosen origin **completed machine run** or **kept completed machine result**; neither is a supplied unperformed run. A half-run, setup, prediction, expected-results lookup, worked example or planning-copy outcome is not eligible. The planning board may still be used normally; this bridge does not turn its cup/low-path counts into a second dataset.

The invitation action takes an explicit finite `caseId` and source kind (`current-completed|kept-completed`). Resolve that case directly, not whichever case happens to be selected later. Read a complete `rainResult(state, caseId)` or that case's valid kept result and clone the **entire existing result snapshot**: case/configuration, model ID/capacity/batch size/notice, both complete tray ledgers, source support and familiarity. Validate it with the same exact semantic result validator as Rain Paths. Expose a narrow pure validator if needed; do not recreate final rows from an expected-count table, strip provenance or run a replacement simulation.

The UI passes the exact eligible source snapshot shown beside the clicked invitation, captured in its current render context **after render-time exposure registration**. In particular, a valid imported completed run must not become immediately stale merely because displaying it advances the established familiarity metadata. The action re-resolves the explicit case/origin and requires semantic equality with that shown snapshot before cloning; a changed source requires a fresh invitation, not a silent substitution. This is one temporary equality check, not a saved hash or revision registry. The click freezes the source before saving/navigating. Navigation alone never creates or refreshes a source. If the source is no longer complete/available, retain all drafts and explain that the original result is unavailable; do not substitute the current case, another kept result or a fresh default. Restarting the original machine, changing its selected case, using a plan, adding support, reloading, or later replacing a kept machine result cannot change the chart's frozen source. A valid frozen chart source remains usable when the live Rain Paths root is absent or unavailable.

Use `#living/notebook/rain` for this branch, with explicit links back to `#science/rain` and the cress `#living/notebook`. Keep the two notebook entrances plainly named **Seedling charts** and **Rain Paths charts**. Entering either branch restores that branch's own current case/page and never changes the other branch's selection. Returning from the chart leaves Rain Paths' `currentCase`, `page`, progress and saved per-case `views` exact; the only permitted cross-loop writes are the narrow exposure flags and their established sticky familiarity metadata described below. A saved chart may name a case different from the current machine; show the frozen source's case label prominently.

If this case already has a chart, the ordinary invitation offers **Return to this chart draft**. It does not reset entries or replace its source, even when the new invitation has a different source-support snapshot. Offer a separate explicit **Replace this case's chart draft with this result** action with adjacent text explaining that it clears current selected rows, bar values and pending response fields, while retaining this case's earlier checks and latest kept chart. This is an intentional restart with the newly frozen source, marked familiar; it never overwrites another case. No invitation automatically replaces unfinished work.

## One source packet, four relevant-or-irrelevant datum rows

Derive four selectable datum rows from the one frozen completed result, without saving a second authoritative set of counts:

| Local datum ID | Category | Quantity | Value from frozen source |
| --- | --- | --- | --- |
| `A:runoffNew` | Tray A | New runoff | A `runoffNew` |
| `B:runoffNew` | Tray B | New runoff | B `runoffNew` |
| `A:storedNew` | Tray A | Newly stored | A `storedNew` |
| `B:storedNew` | Tray B | Newly stored | B `storedNew` |

IDs are scoped to the draft's frozen source/case; they are not universal observation IDs. All rows say **model-water tokens**. Keep the complete source controls available: case, entrance/lid, earlier stored tokens and new input **on each tray**. Earlier stored tokens are context, not new rain or a new-water destination. The source notice stays beside the source table, chart and kept chart: the tokens and exact machine rules are invented, not measured rainfall or real units.

The frozen original question is: **After N new tokens on each tray in this machine comparison, which tray had more new runoff, and how many more?** Include the case label/changed factor. The optional difference does not become a causal-explanation task.

Choose up to two datum rows with native selection controls. Full category, quantity and source value stay visible; both row selection and removal are reversible. At the two-row limit, explain how to remove a row rather than silently replacing one. Selected order determines bar order. A newly selected row starts blank; values remain only with rows that remain selected. Removing/readding a row cannot relabel another row's number.

“Check my data” distinguishes missing rows, two different quantities, a same-tray pair, a pair of newly-stored rows, and the requested new-runoff pair (one row per tray). Reversed A/B order is equally relevant. Keep unusual selections editable and chartable. This four-row packet gives data selection a purpose without fabricating other completed trials or forcing the learner to run all four cases first.

For implementation acceptance, the eligible completed source counts are:

| Case | A newly stored / new runoff | B newly stored / new runoff | Requested B-minus-A runoff difference |
| --- | --- | --- | --- |
| `cover-12` | 12 / 0 | 0 / 12 | 12 |
| `cover-24` | 12 / 12 | 0 / 24 | 12 |
| `space-12` | 12 / 0 | 4 / 8 | 8 |
| `space-24` | 12 / 12 | 4 / 20 | 8 |

This table is a specification oracle, not an in-app substitute for completing a run. The original question's correct tray is B in these four authored cases; do not invent a tie or random result to diversify it. Ties, zeros and reversed bar order remain meaningful when reading the learner's own draft.

## The existing four-turn construction loop

Reuse the Field Notebook's **Data → Build → Read & check → Keep or revise** pattern, 44px controls, local narration, source-versus-draft distinction and task-specific help. All pages are open; missing data explains why a particular check has no answer, rather than locking navigation.

**Data.** Keep the frozen question and four candidate rows together. Mark the packet as a completed result carried from Rain Paths; do not label it a cress observation, a physical measurement or newly collected independent evidence. Selecting rows does not alter the machine or call its Keep action.

**Build.** Use a fixed shared horizontal numerical axis **0–24**, with major ticks at **0, 4, 8, 12, 16, 20, 24**, for both categorical bars. Values accept every integer in 0–24, including entries between ticks. Bar lengths are proportional, begin at zero and use the same scale; no separate autoscaling or snapping to the source. The axis unit is fixed and always visible: **model-water tokens**. Do not offer mm, litres or rainfall depth as unit choices, and do not reuse the cress chart's fixed 0–70/mm geometry.

The quantity selector offers **New runoff / Newly stored / not chosen**. Category labels are derived accurately from each selected datum (for example “Tray B — newly stored”); an incorrect quantity label stays the learner's visible draft. The supplied table keeps its own correct labels. A source-faithful chart of the two newly-stored rows can be irrelevant to the runoff question; the app must be able to express that distinction.

Each applied value begins `null` (blank), not zero. Bounded raw input (up to 16 characters) remains separate from applied values through pages, cases, support, navigation and reload. Set bar, Clear, and ±1/±4 touch controls reuse the established pattern. An invalid raw entry remains exactly as typed; adjustment does not silently fall back to a stale applied number. “Apply entries and check” validates every selected pending field first and applies them together, or leaves the draft/check history unchanged and explains which entry needs editing. Empty text may remain blank; a zero entry draws a labelled zero marker. No copied source answer is applied on render, selection or narration.

**Read & check.** Retain three separate prompts and outcomes:

1. **Read my draft:** compare the first and second entered bars, or select same. Evaluate the actual entered values, even when they disagree with the source or use irrelevant rows. With fewer than two applied values, explain the missing value without recording an answer.
2. **Check my source:** do the two entered values and chosen quantity agree with the selected frozen datum rows? Fixed token units remain visible. A pair of newly-stored rows with the newly-stored label and correct entries can agree with its source while being irrelevant to the original question. Mixed quantities cannot both agree with one quantity label. Report source agreement and question relevance separately.
3. **Answer the original question:** show the requested frozen A/B new-runoff rows explicitly beside choices **Tray A / Tray B / same / not sure**, plus a separately optional whole-token absolute difference in 0–24. Use the requested source pair regardless of the learner's current row selection or incorrect chart. Do not silently correct the draft when answering this question. Preserve the raw choice/difference form before submission; blank optional difference is different from zero. A valid wrong answer is retained, without penalty.

“Check my chart” gives separate feedback for row relevance, quantity-to-selected-row agreement and each applied bar. It must not compress these into one pass. The original question's requested runoff quantity is another relevance check, not a reason to call an accurately labelled stored-water chart unfaithful to its source. Every checked result freezes the exact source, selected IDs/order, entered and raw pending values, question, support and familiarity at that moment. Later help or edits do not rewrite it. Editing after a check labels the visible feedback as an earlier check until checked again.

**Keep or revise.** Keep any draft, including empty, partial, irrelevant or mismatching work. Freeze its full source, labels, selected rows, applied and pending entries, current question and latest separate checks. One latest kept draft per case is enough, marked revised on a later explicit Keep. Keeping is not passing or completing another experiment. Earlier checks stay bounded and frozen. Keep the unscored “I chose these rows because… / I would change…” conversation invitation; no free-text storage or grading is needed.

Help can explain the current labels/rules, narrate the turn or record together work. A worked chart example, if offered, must use another already-imported valid source and be labelled familiar supplied support; hide that option if no other imported case exists. Do not fabricate or auto-complete another Rain run to supply a different example. The source strip is available on every page, with compact labels beside the current action on narrow screens.

## State: a narrow extension, no new top-level destination

Add one optional `rain` version-1 branch to the existing `fieldNotebook` root. Keep the existing root version, eight cress cases, cress current case/page/read prompt, source-day browser, exposed days, checks, source descriptors and kept charts unchanged. Existing cress actions must preserve this branch byte-for-byte unless a water-specific action explicitly changes it. Existing water-machine actions must not mutate it.

The cress validator must recognise `rain` as an allowed **opaque optional branch**, preserving any JSON payload there without consuming or repairing it. A separate water selector strictly validates that branch. This small separation is necessary: a malformed/future water-chart branch must make only the water charts unavailable, not disable or rewrite valid cress charts. Unknown keys elsewhere in the cress root retain its existing strict behaviour. An unavailable/future whole `fieldNotebook` root stays exact; water invitations must not call a destructive full-root recovery or replace it to get a fresh chart. Offer the established explicit keep-original recovery separately.

The water branch stores only:

- `version:1`, current case ID (or null before import), sticky `resultsExposed` and `exposureUnknown`, at most four finite case records, and optional raw `recovered`.
- Per case: frozen source wrapper `{origin, result}` using the existing complete Rain result shape; selected datum IDs (zero to two); applied values keyed only by selected IDs (integer 0–24 or null); matching pending bar strings; quantity (`runoffNew|storedNew|null`); pending original-question choice/difference; sticky support per Data/Build/draft-reading/source-check/original-question/Keep task; `familiar:true`; at most 24 checks total; latest kept chart; and saved `views` containing that case's page and reading subprompt.

The separate saved views follow Rain Paths' now-persisted per-case view pattern. Do not reintroduce module-level tray/question/page globals for water-chart selection. Changing case returns its exact chart/page/form; a case without an imported source cannot acquire a synthetic draft from the case selector. Switching cress/water routes and explorers restores each independent view.

No extra source registry, revision counter, timestamp, UUID, integrity ledger or history service is required. The case ID plus the embedded exact result establishes the source. Candidate datum counts derive from that result; no second mutable count table is saved. Checks/kept drafts embed their source because they can outlive an explicit current-source replacement. Validate those embedded snapshots independently rather than comparing every old snapshot to the new current source.

Read helpers/renderers are pure and missing branch means no imported water source. Explicit invitation may create a fresh known cress root only if the root is missing; it may add the water branch to a valid existing root. A malformed/future/unknown-key water branch remains exact and unavailable until an explicit **retain this original water-chart record and start fresh** action stores the entire old branch under `recovered`, sets sticky unknown and leaves every cress field unchanged. Unsupported source/model/adapter versions remain recoverable, not regenerated from today's content. Do not coerce counts, silently drop a bad case/check, trust a malformed payload as an observed source or erase unknown work during import/export.

Water actions directly cover invite/return/explicit replace, choose an already imported case, set page/read prompt, toggle datum, set quantity/applied/raw bar input, preserve original-question pending form, request task support, check data/chart, answer the three reading prompts, keep and recover the water branch. They mutate only that valid branch (apart from explicit creation of an absent known outer root). Save raw input before any rerender/navigation. No separate progress-transfer destination key is needed: the existing `fieldNotebook` payload carries this extension, including unsupported raw branches, through save-off, explorer switching, local export/import and reset.

## Exposure, support and familiarity across the bridge

All water-chart checks are `practice:true` and familiar from the start: they reuse a completed supplied machine result and expose its source values. Preserve source support/familiarity verbatim, and store chart-task support separately. Do not imply that no chart help means the source was independently generated, the model pack was unseen or the learner has demonstrated experimental design. Numerically matching bars do not establish causal understanding or independent chart construction after a worked example.

Add a narrow pure water-chart display-exposure helper. Actual visible source packets, selected-source strips, requested question pairs, worked examples, kept chart sources and opened raw notes expose results from the Rain Paths pack. An empty water entrance without a source does not. The app records actual views into the water branch's sticky `resultsExposed`/`exposureUnknown` and applies the same pack-level flags through `noteRainDisplayExposure`. The existing hook may also advance each Rain case’s sticky `familiar` metadata. Preserve Rain Paths first predictions and its active case/page/views/trial/plan state, including all ledgers and frozen checks. This is the established narrow hook, not a new exposure system. Known exposure still takes precedence over uncertainty; later prediction revisions must not become before-results merely because the chart is closed or the machine restarted.

If the live Rain root is unavailable, keep it exact; the independently validated frozen chart remains readable and its own known displayed exposure is retained. When Rain Paths is explicitly recovered, replay the valid water branch's saved known/unknown flags through the existing narrow hook before accepting another prediction. A known displayed frozen result yields after-results even alongside sticky unknown. An unavailable whole notebook or unavailable water branch cannot supply trusted known counts: conservatively propagate unknown, without reading arbitrary raw payload fields. A missing water branch in a known cress format is known absent, not unknown. Water-branch recovery retains uncertainty, and an earlier first prediction is never rewritten.

Route exposure dispatch must distinguish the two notebook branches. `#living/notebook/rain` must not expose cress days simply because the preserved cress root still has a selected day, case or kept chart. Cress views continue using their existing day hook; actual water views use the Rain pack hook. Opened full notes may legitimately expose both families because their respective saved records are actually displayed. Keep both hooks narrow; no universal learner profile.

The bar axis, values, ticks at intervals of four, and two unrelated counts are not by themselves multiplication exposure. This slice draws bars rather than storage arrays and does not explain six groups of four. Return no shared-fact pairs for an ordinary water chart/table/narration. If implementation actually displays Rain's 3×4 machine storage, a 2×4 prior-token array or an explicit grouped multiplication/division example, report exactly that representation through the existing shared hook, including in kept views/notes, and create no arithmetic answer or recall record. Prefer the simpler labelled source table here so extra array teaching is unnecessary.
