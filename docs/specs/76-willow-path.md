# 76 — Willow Path: count on to the bridge

Status: **author specification and source audit complete for independent specification and content review; not built or cleared to build**. This narrows the [reviewed proposal](proposed/willow-path.md) to one original 1–10 path and resolves its event-text/source ambiguity. See [source audit 76](../source-audits/76-willow-path.md) for primary papers, Jane/Marble checks and the limits of the research comparison. All learner-facing lines below are original. No paper or upstream artwork, code or prose is incorporated.

## Purpose and research boundary

Add `#numbers/path` as an always-open Number Garden activity. From the garden gate, Leaf and Lantern walk along ten equally spaced stones to Willow Bridge. A spinner offers 1 or 2; each press moves the active token to exactly the next numbered stone and invites people to say the stone's number. The board is one horizontal row, numbered 1–10 left to right, with an unnumbered gate at position 0. Equal moves cover equal distances. At 320 CSS pixels, all ten numerals and both distinguishable token shapes must remain legible without horizontal page scrolling, wrapping, a second row or hover. A text line states the active token, position and next square independently of color. The gate can be a separate compact marker outside the ten equal stones.

The papers in [audit 76](../source-audits/76-willow-path.md) establish the source design's linear layout, 1/2 spinner and naming the *arrival-square numbers* as the token moves. They do not test this digital app, its cooperative both-arrive ending, optional solo play, optional narration, town events or unrecorded speech. The app makes no learning-effect or mastery claim. This path records positions only, not a child's counting, correctness, support, speech, turns taken, comparative skill or social behavior. No microphone, automatic speech scoring, winner, time, points, reward, penalty or prerequisite lock.

## One finite board and its complete copy

The only authored source is `willow-ten`, version 1. Its complete source is copied into a walk at explicit Start. The source contains `squares:10`, `spinner:[1,2]`, numerals derived in order from 1 through `squares`, all authored text below and the three event records with their **full** title and body. Event codes alone are insufficient. The UI never looks up current catalog text to render an existing walk. The destination numeral on `Step to 4`, the remaining-step count and dot count are mathematical views of the stored spinner/position, not a new content lookup. Static words on the controls also come from the stored copy. If current catalog copy changes later, a saved walk still shows its own board, event, help, arrival and ending text. The only placeholders admitted in `source.text` are `{token}`, `{value}` and `{square}` in the named fields above, replaced by an enum token or bounded integer before escaping; all other braces are literal.

## Turn and arrival contract

The mode is chosen before Start and saved as `two` or `solo`; both modes run the **same** two-token turn machine. It describes human arrangement only. The app does not assign a real person to a token or infer turn-taking behavior. Leaf starts. Starting a walk positions both tokens at 0, with `spin:null`, `turn:'leaf'`, `done:false`.

`Spin` is enabled only for an unarrived active token with no pending spin. It chooses 1 or 2 with equal probability and sets `spin:{value,stepsLeft:value}`. A second spin is unavailable until that turn ends. The result is exposed by text and the matching dots, never color alone. Each `Step to n` press increments the active token by exactly one, decrements `stepsLeft`, and announces the **new** square. A token never jumps from 3 to 5 on one press. The step button keeps focus during a multi-step turn; after a pass, focus goes to the next Spin control with the turn line announced once. No animation is needed; respect reduced motion.

On reaching stone 10, discard unused steps and clear `spin` immediately. From 9 with a spin of 2, one tap lands on 10, the arrival line appears, and the other token gets the turn. If `stepsLeft` reaches zero below 10, clear `spin` and pass to the other unarrived token. Once one token has arrived, every subsequent turn belongs to the other until it reaches 10; the arrived token is never offered Spin. When the second arrives, set `done:true`, `spin:null` and show the exact both-arrived line. There is no display, save field or narration of who arrived first. A fresh walk is always available through an explicit, confirmed new start; every other destination stays open. The path offers no later track length or spinner variant in this increment.

## Saved walk, source validation and recovery

Optional root `willowPath` is absent until the first explicit Start. Its readable form is `{version:1,nextId,walk,retainedRaw?}`. `walk` is null or `{id,source,mode,positions:{leaf,lantern},turn,spin,done}`. There is only one current walk, no past-walk array and no participation counter. The `source` snapshot holds `version:1,id:'willow-ten',squares:10,spinner:[1,2],text:{...},events:[{square,title,body},...]`. The text object contains each authored string in the table, including mode, controls, event affordance, adult tip, help, arrival and ending lines. Dynamic labels interpolate only token enum and integer square/step values; no HTML from saved text is trusted. Store no event-open state, speech use, player identity or support flag.

Accept a readable v1 walk only when its own source is structurally complete: `id:'willow-ten'`, `squares:10`, `spinner:[1,2]`, exactly the three distinct event squares 3, 6 and 8 with complete title/body text, every named `text` field present as a bounded string, and source JSON below 16 KiB. A historical source with different **wording** is valid; source words are never compared with today's catalog. Square numerals follow from its own `squares` field, not a separate label array. The model validator uses the source's `squares` to check integer positions, including a synthetic 20-stone source; that synthetic structure remains read-only recovery because this release renders only `willow-ten` 1–10. Unknown source versions or layouts remain raw recovery. For a readable source, both positions are integers in `0..source.squares`; `mode` and turn are known enums; `spin` is null or has a value in `source.spinner` and integer `stepsLeft` in `1..value`; `done` is true exactly when both positions equal `source.squares`. A completed walk has no spin. A turn never names an arrived token while the other is walking. One arrived token plus another mid-turn is valid. Do not infer whether a spin result was truly random from saved state.

`id` is `walk-<positive safe integer>`. `nextId` is a positive safe integer greater than the current valid walk's suffix; allocation refuses without mutation if increment would exceed safe-integer range or conflict with the current ID. A new Start copies the authored source only after checking its 16 KiB cap, then allocates the next ID. For an absent root, begin at `walk-1`; a valid root increments its `nextId`. New start replaces only the active walk after confirmation. No old walk is silently trimmed or normalized on render, reload, switch, notes, export, or import.

An invalid/future `willowPath` root or unreadable `walk` is **not repaired in place**. The path shows a recovery panel: **This saved walk cannot be opened here. Its original record is still in your notes. You can start a separate walk.** The panel offers notes, the Number Garden map and a confirmed fresh Start; it never calls a current-board answer or event lookup on that raw record. On explicit new Start, copy the entire parsed original `willowPath` value without normalization into `retainedRaw` before installing the new readable root. Keep an already-present `retainedRaw` when replacing a readable walk. If preserving the existing raw value would require overwriting another `retainedRaw`, refuse Start and keep the original root. If persistent storage is full, keep the complete new root and `retainedRaw` in the current in-memory session, show the existing save warning and permit notes download; do not claim a durable save. Notes identify retained recovery without placing arbitrary raw data into HTML; the full parsed value remains unchanged in the JSON download. Any raw field shown in notes is escaped. If an imported JSON file has exact original text beyond the parsed state, the existing transfer recovery copy retains that file separately. A fresh global explorer reset follows existing explicit reset semantics; it clears this root with the rest of that explorer only after the existing confirmation.

The root is included in normal local save, save-off memory, explorer isolation, notes JSON download and report-wrapper import. `prepareProgressImport` must accept a bounded readable Willow root and preserve future/malformed raw Willow data, including a `retainedRaw` field, without changing unrelated roots. If the shared importer cannot safely preview a malformed value, it must refuse the import without touching current explorers; never silently discard the Willow value. The current import file limit stays 5 MiB. New-source size and ID checks protect allocation, not a reason to evict older raw recovery data. Grown-up notes say **A Willow Path walk is waiting: Leaf on {position}, Lantern on {position}.** or **No Willow Path walk is in progress.** Position 0 reads **at the gate**, position 10 reads **at the bridge**. The notes describe positions only, no inferred counting success or social evidence. They link to the raw recovery details when applicable.
