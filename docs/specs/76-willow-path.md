# 76 — Willow Path: count on to the bridge

Status: **local implementation and independent implementation review cleared; draft, unmerged and undeployed**. This narrows the [reviewed proposal](proposed/willow-path.md) to one original 1–10 path and resolves its event-text/source ambiguity. See [implementation receipt](../reviews/76-willow-path-implementation-review.md), [specification review receipt](../reviews/76-willow-path-spec-review.md) and [source audit 76](../source-audits/76-willow-path.md) for the primary papers, Jane/Marble checks and the limits of the research comparison. All learner-facing lines below are original. No paper or upstream artwork, code or prose is incorporated.

## Purpose and research boundary

Add `#numbers/path` as an always-open Number Garden activity. From the garden gate, Leaf and Lantern walk along ten equally spaced stones to Willow Bridge. A spinner offers 1 or 2; each press moves the active token to exactly the next numbered stone and invites people to say the stone's number. The board is one horizontal row, numbered 1–10 left to right, with an unnumbered gate at position 0. Equal moves cover equal distances. At 320 CSS pixels, every numeral is at least 16 px and both distinct, labeled token shapes fit **stacked within** one equal-size stone when together. Stone 10 keeps its numeral; the bridge name appears below the track at that end, not as a further numbered step. The compact gate sits outside the ten equal stones. No horizontal page overflow, wrapping, a second row or hover. A text line states the active token, position and next square independently of color.

The papers in [audit 76](../source-audits/76-willow-path.md) establish the source design's linear layout, 1/2 spinner and naming the *arrival-square numbers* as the token moves. They do not test this digital app, its cooperative both-arrive ending, optional solo play, optional narration, town events or unrecorded speech. The app makes no learning-effect or mastery claim. This path records positions only, not a child's counting, correctness, support, speech, turns taken, comparative skill or social behavior. No microphone, automatic speech scoring, winner, time, points, reward, penalty or prerequisite lock.

## One finite board and its complete copy

The only authored source is `willow-ten`, version 1. Its complete source is copied into a walk at explicit Start. The source contains `squares:10`, `spinner:[1,2]`, numerals derived in order from 1 through `squares`, all authored text below and the three event records with their **full** title and body. Event codes alone are insufficient. The UI never looks up current catalog text to render an existing walk. The destination numeral on `Step to 4`, the remaining-step count and dot count are mathematical views of the stored spinner/position, not a new content lookup. Static words on the controls also come from the stored copy. If current catalog copy changes later, a saved walk still shows its own board, event, help, arrival and ending text. The only placeholders admitted in `source.text` are `{token}`, `{value}` and `{square}` in the named fields below, replaced by stored display names or bounded integers before HTML escaping; all other braces are literal. Each text key substitutes only its required placeholder set listed in the validation contract; all other placeholders remain literal. Substitution is single-pass: braces inside a stored token display name are never evaluated again.

## Turn and arrival contract

The mode is chosen before Start and saved as `two` or `solo`; both modes run the **same** two-token turn machine. Show the saved mode's exact source label next to the board throughout the walk. It describes human arrangement only and cannot change mid-walk; a different mode requires a new walk. The app does not assign a real person to a token or infer turn-taking behavior. Leaf starts. Starting a walk positions both tokens at 0, with `spin:null`, `turn:'leaf'`, `done:false`.

`Spin` is enabled only for an unarrived active token with no pending spin. It chooses 1 or 2 with equal probability and sets `spin:{value,stepsLeft:value}`. A second spin is unavailable until that turn ends. After Spin, move focus to the next Step control and announce the stored `spinResult` once through the active announcement channel (local voice when enabled, otherwise the live region). The result is exposed by text and matching dots, never color alone; the decorative dots are hidden from assistive technology because the value is already in text. Each `Step to n` press increments the active token by exactly one, decrements `stepsLeft`, and announces the **new** square. A token never jumps from 3 to 5 on one press. The step button keeps focus during a multi-step turn. When a turn passes, focus goes to the next Spin control; the status announcement names the next turn. When a token arrives first, one announcement includes the arrival line **and** next turn. When the second arrives, focus moves to the ending line, not a nonexistent Spin control. With local step voice off, these announcements use one live region. With step voice on, disable those live-region updates and use local speech for the destination and applicable turn/arrival/ending line instead. Ordinary focus labels and visible status remain in both modes. This controls the app's own two announcement channels, without promising a particular external screen reader's audio behavior. No animation is needed; respect reduced motion.

On reaching stone 10, discard unused steps and clear `spin` immediately. Stone 10 retains its numeral and equal width. Put the bridge label below the track at that end, not inside or beside its narrow cell. Token names appear in the legend and status lines; only the two distinguishable shapes are stacked within a stone. The arrival line replaces the ordinary `atStone` position line. From 9 with a spin of 2, one tap lands on 10, the arrival line appears, and the other token gets the turn. If `stepsLeft` reaches zero below 10, clear `spin` and pass to the other unarrived token. Once one token has arrived, every subsequent turn belongs to the other until it reaches 10; the arrived token is never offered Spin. When the second arrives, set `done:true`, `spin:null` and show the exact both-arrived line. There is no display, save field or narration of who arrived first. A fresh walk is always available through an explicit, confirmed new start; every other destination stays open. The path offers no later track length or spinner variant in this increment.

## Saved walk, source validation and recovery

Optional root `willowPath` is absent until the first explicit Start. Its readable form is `{version:1,walk,retainedRaw?}`. `walk` is null or `{source,mode,positions:{leaf,lantern},turn,spin,done}`. There is only one current walk, no ID, past-walk array or participation counter. The `source` snapshot holds `{version:1,id:'willow-ten',squares:10,spinner:[1,2],text:{...},events:[{square,title,body},...]}`. The required `text` keys are exactly the ones in the copy table, including token names, mode, controls, event affordance, step-voice labels, adult tip, help, arrival and ending lines. Additional unfamiliar keys in a saved root, walk, source or text object are preserved but ignored, not a reason to lock an otherwise readable walk. Dynamic labels interpolate only the known token enum and source-bounded integer square/step values; no HTML from saved text is trusted. Store no event-open state, speech use, player identity or support flag.

Accept a readable v1 walk only when its own source is structurally complete. The supported **numeric layout** is fixed in code at `squares:10, spinner:[1,2]`, independent of today's authored catalog. `source.id` matches `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, not necessarily `willow-ten`; the current authored pack uses `willow-ten`. The saved source may have **zero through ten** event records, each with a distinct integer `square` in `1..source.squares` and its complete stored title/body. Do not require today's event count, event positions or event wording. The `text` field is a plain object and `events` is an array of plain objects. Every required `text` value and event body is a string with non-whitespace content and 1–512 UTF-8 bytes; every event title is a string with non-whitespace content and 1–120 UTF-8 bytes. `source.id` is at most 64 ASCII bytes. Required templates retain their semantic placeholders: `spinButton`, `turnLine`, and `atGate` contain `{token}`; `spinResult` contains `{token}` and `{value}`; `atStone` contains `{token}` and `{square}`; `stepButton`, `eventButton`, and `eventHearButton` contain `{square}`. These are structural requirements for naming a token or destination, not comparisons with current catalog wording. Unknown extra keys, including in positions, spin and event records, remain preserved and ignored. `JSON.stringify(source)` is at most **16,384 UTF-8 bytes**. A historical source with different copy or events is valid and rendered from itself. Square numerals follow from its own `squares` field, not a separate label array. Unknown `source.version` or numeric layouts remain exact raw recovery. This is an explicit departure from the proposal's playable synthetic 20-square test: this release has no reviewed 20-square phone rendering. Position bounds for a supported walk use its own `source.squares`, never a current catalog count; a later release can add supported layouts without migrating existing walks. For a readable source, both positions are integers in `0..source.squares`; `mode` and turn are known enums; `spin` is null or has a value in `source.spinner` and integer `stepsLeft` in `1..value`; `done` is true exactly when both positions equal `source.squares`. A completed walk has no spin. A turn never names an arrived token while the other is walking. One arrived token plus another mid-turn is valid. Do not infer whether a spin result was truly random from saved state.

A build test confirms that today’s authored source is below the byte cap; the refusal path is defensive. The only new-copy cap is the source's 16,384-byte UTF-8 limit; if today's authored source exceeds it, Start refuses without replacing an existing walk and gives the code-owned notice **That new walk cannot start in this version. Any current walk stays as it is.** An absent root starts empty and creates a walk only on Start. New Start replaces only the active walk after confirmation. No old walk is silently trimmed or normalized on render, reload, switch, notes, export, or import.

An invalid/future `willowPath` root or unreadable `walk` is **not repaired in place**. The path shows a recovery panel: **This saved walk cannot be opened here. Its original record is still in your notes. You can start a separate walk.** The panel has code-owned links **Grown-up notes** and **Back to Number Garden**, and a **Start a separate walk** button. That button opens the code-owned confirmation **Start a separate walk? The earlier record stays in your notes.** with **Keep the earlier record** (cancel) and **Start a separate walk** (confirm). Recovery UI uses these current application strings, never text from the unreadable record. The panel offers notes, the Number Garden map and a confirmed fresh Start; it never calls a current-board answer or event lookup on that raw record. `retainedRaw` accepts **any JSON value** and is never interpreted or validated as a walk. On explicit new Start from unreadable data, copy the **whole parsed old root**, including any prior `retainedRaw`, into the new root's `retainedRaw`; nesting preserves every layer exactly. On replacing a readable walk, keep its existing `retainedRaw` unchanged. Nested prior recovery alone does not block a fresh Start. Before nesting an unsupported root, preflight the resulting whole notebook against the existing import depth, node and UTF-8 byte limits, including the actual formatted notes-report wrapper. If it cannot round-trip, leave the original unchanged and show a focused notice directing the user to download it and start a separate explorer. This refusal does not affect ordinary new walks, replacement of a readable walk or playing an existing walk. If persistent storage is full, keep the complete new root and `retainedRaw` in the current in-memory session, show the existing save warning and permit notes download; do not claim a durable save. Notes identify retained recovery without placing arbitrary raw data into HTML; the full parsed value remains unchanged in the JSON download. Any raw field shown in notes is escaped. If an imported JSON file has exact original text beyond the parsed state, the existing transfer recovery copy retains that file separately. A fresh global explorer reset follows existing explicit reset semantics; it clears this root with the rest of that explorer only after the existing confirmation.

The root is included in normal local save, save-off memory, explorer isolation, notes JSON download and report-wrapper import. Add `willowPath` to the shared importer's `destinations` map **and** its allow-list of optional roots permitted to hold non-object raw values. `prepareProgressImport` accepts a bounded readable Willow root and preserves future/malformed raw Willow data, including arrays, strings and `retainedRaw`, without changing unrelated roots. Its detached `destinationNotes` preview must return safely for every such value; it may show only a generic recovery line, never stringify arbitrary raw data into HTML. Existing prototype-key/depth/node/file limits still apply; a file rejected under those global safety rules leaves current explorers untouched and keeps the original file externally. The current import file limit stays 5 MiB. New-source size checks are not a reason to evict older raw recovery data.

Grown-up notes use **No Willow Path walk has started.** when no walk exists, **A Willow Path walk is waiting. Leaf {leaf position}; Lantern {lantern position}.** while in progress, and **The Willow Path walk is complete. Leaf at the bridge; Lantern at the bridge.** when done. Each position phrase is exactly **at the gate**, **on stone {square}**, or **at the bridge**; there is no extra “on” prefix. A recovery-only root says **An earlier Willow Path record is kept in this download.** For a readable walk, substitute its stored `tokenLeaf` and `tokenLantern` for the default Leaf/Lantern names in these notes lines. A readable root with `walk:null` and `retainedRaw` shows the no-walk line plus the earlier-record line; an unreadable root shows only the earlier-record line. A readable walk with retained recovery adds the earlier-record line alongside its position or completion line. Notes describe positions only, no inferred counting success or social evidence, and identify retained raw recovery when present.
