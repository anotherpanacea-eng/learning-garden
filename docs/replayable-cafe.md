# A café to keep playing

## Experience

Add a replayable Almost-Right Café alongside the existing introductory café story. The home café button opens the game at #cafe; the original café story remains available in the adventure hub and through an invitation in the game. Preserve all existing stories, math records, routes, guides, explorer choices, and browser origin. All guests, food, and examples are imaginary; no identity, free-text fields, accounts, analytics, network calls, or learner-specific fixtures.

The play surface is a café counter: one expressive illustrated guest and order ticket beside a visible cupboard of eight silly ingredients. Keep the existing forest #183f39, mint #eaf4ef, yellow #e9b84a, pink #da8d8d, and paper #fffef9 palette, Georgia story headings and Trebuchet controls. Jars, plates, and an order ticket carry the visual identity. Avoid turning the scene into a quiz-card grid. Tap buttons and keyboard controls; no drag, timers, money, grades, penalties, leaderboard, failure ending, or mandatory completion.

Each successive order chooses a different authored guest and changes wishes, party size, and plate size. A seeded local order sequence provides reproducible saved visits and does not repeat the immediately prior order. Use eight fictional guests, eight ingredients with explicit warm/cold, crunchy/soft, sweet/tangy properties, and requests drawn from two different property axes. Every request has multiple possible plates. Quantities stay small: 2–4 guests, 2–3 bites per plate. One bite is one unit from a jar. Plates can combine ingredients; a request for something warm and something crunchy is satisfied if the plate includes at least one bite with each property, including from different ingredients. State that rule explicitly; do not claim the whole mixed dish is warm. Repeated bites of the same ingredient are allowed. Names never determine correctness.

## One order

1. **Make a plate:** Fill exactly the requested number of bite slots with cupboard ingredients using plus/minus controls. All requested properties must appear. Ingredients may be chosen even when stock is insufficient, because top-up is always available later. Check the plate with descriptive feedback, and accept every valid combination.
2. **For the table:** Work out total bites = number of guests × bites per plate. A helper can show/count one equal plate at a time or reveal an explanation. Wrong answers invite another try; skip-to-next-stage remains explicit and counts as support, never a correct independent answer.
3. **Cupboard:** Show each selected ingredient's required count and stock. Ask how many bites need adding altogether, summing positive per-ingredient shortages. A difference of zero is valid and explained. An optional tap-controlled picture/shortfall explanation provides support. After a correct answer OR explicit supported skip, “Top up and serve” adds exactly missing units then deducts all portions. Stock is never negative, and serving cannot repeat on a reload or double click.
4. **Visit again:** Guest responds to the plate, and child can invite the next guest indefinitely, pause, or restock all jars. Restock is only between orders; no mid-question answer-key changes. No next guest is created automatically on render/reload. The guest/order/recipe/inputs/attempts/help stage survive pause, route changes, and reload. No challenge is required to reach future guests; a whole-order “Let this guest wait; invite another” option records a skip and changes no stock.

Correctness applies to plate constraints and arithmetic only. Do not infer general level, empathy, nutrition, mastery, or independent reading. All game activity is practice; notebook makes that clear. Keep plate checks, arithmetic attempts, skips, and support separate; viewing pictures or solutions remains support even after “I knew it.” No method/reading claims are inferred. Record no fresh assessment evidence from this game.

## State and integration contract

New modules: cafe-content.mjs (authored ingredients/guests/wish pairs), cafe-core.mjs (pure game actions/state), cafe-ui.mjs (render/bind interface via app actions). state.cafe contains version:1, seed (positive integer), nextOrder (nonnegative integer), stock:{ingredientId:integer 0..30}, current, history (last 24 summaries), served count. Current contains orderIndex, stage ('plate','total','stock','served'), recipe:{ingredientId:integer 0..3}, plateAttempts, total:{input,attempts,supported,skipped}, shortfall:{input,attempts,supported,skipped}, served:false/true. Derive guest/request/counts from seed+orderIndex and authored data instead of trusting saved answer keys. Do not persist duplicate generated answer keys. Non-current history is bounded; served count is parent-facing only, not a reward meter.

ensureCafe must recover malformed additions conservatively without discarding legacy progress or crashing notes/home; clamp validated fields, filter history, and make malformed/inconsistent unserved current order recover to a safe plate stage without spending stock. A served flag, served stage, or matching history record makes that order closed: recover to a served/retired screen, never reopen it or spend its stock again, even if other saved fields disagree. Reject array/nonobject containers. Normalize missing support arrays. Numeric inputs must use existing whole-number parsing and core validation. Once stage advances, earlier plate data is fixed for that order. Only a serving action mutates stock; active-order skip leaves it unchanged. Serve is idempotent. Only the latest created order index can remain active; older cursors retire even after their history entry has expired. No replay of spent stock through stale cursors. A valid served state reload resumes the response screen. New guest advances order counter once, and nothing else advances it.

Expose ensureCafe(s), orderFor(c), currentRecipe(c), checkPlate(s), adjustBite(s,id,delta), submitCafeNumber(s,value), supportCafe(s), skipCafeStage(s), serveCafe(s), nextGuest(s), skipGuest(s), restockCafe(s), cafeSummary(s), plus authored data. Action functions validate stages and values; they return false on invalid mutations. UI actions use namespaced data attributes. renderCafe(state) and cafeNotes(state) render escaped content; bindCafe(state,{save,render,exposeFacts,focus}) attaches listeners only to cafe view. renderCafe must not mutate stock/order counters or register exposure.

ensureCafe runs with other state initializers, and export naturally includes this extension. Original restoreState retains it. Reset fresh state adds an empty café, saving-off applies unchanged. Open game calls ensureCafe and starts its first guest only if current is absent; this must be an explicit app-route action before render, not a side effect of the renderer. Restored malformed game additions must retain valid legacy state. All displayed multiplication pairs (current table count and helper examples if any) feed the existing exact/commuted exposure integration and mark paused baseline/broad/story drafts familiar. Café observations remain separate from baseline/story observations. Introductory story and its evidence stay unchanged.
